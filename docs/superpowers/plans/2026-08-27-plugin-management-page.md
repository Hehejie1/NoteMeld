# 插件管理与内置目录页面实施计划

日期：2026-08-28
基线：`main`  需求：[2026-08-27-plugin-management-page.md](../../requirements/2026-08-27-plugin-management-page.md)

## 目标

在既有 `/settings/plugins` 安装/运行控制台上增加内置插件目录、搜索/分类、详情、已安装筛选和安全的添加入口；保持现有插件 API、权限和版本控制事实源不变。

## 步骤

1. **建立内置 catalog 数据模型**
   - 在插件前端 service 中定义目录项类型和版本化默认目录。
   - 以 `plugin_id` 将目录项与后端 `PluginInstallation` 合并，区分目录状态与安装状态。
   - 验证：类型检查；catalog 不包含凭证、绝对路径或未验证平台的运行承诺。

2. **重做插件页面信息架构**
   - 保留 `/settings/plugins` 和旧生命周期操作。
   - 增加目录/已安装 tab、搜索、分类、状态筛选、卡片和详情弹窗。
   - 验证：页面 contract 检查所有状态、空态、ready gate 和旧 API 调用仍存在。

3. **实现添加流程**
   - 将 URL、SHA-256、权限和安全提示放入“添加插件/内容”弹窗。
   - 添加权限确认和安装中的不可重复提交状态；正式提交仍调用现有 install API。
   - 验证：只有 backend ready 且来源非空时可提交；成功刷新，失败显示安全错误。

4. **补充契约测试与文档同步**
   - 新增前端插件页面契约测试。
   - 更新需求索引/忽略放行规则，检查 API、产品规则和数据模型无需变更。
   - 验证：`pnpm test:contracts`、`pnpm build`、`git diff --check`。

5. **Review、提交与交接**
   - 检查无第二状态源、无敏感信息、无生成物和无无关重构。
   - 提交明确文件；回报 worktree、测试和 commit，等待 `/wt-merge`。

## 取舍

- 首期 catalog 为随前端发布的静态、只读目录，避免在没有后端 catalog API 时新增数据表或网络市场。
- 不增加安装预览 API；现有安装表单在提交前展示用户输入的来源、SHA 和权限确认，后端验证仍是最终权威。
- “添加内容”按标准 Release ZIP 插件包处理，不接受任意文本或任意脚本。
