## 1. 原始需求

用户希望以 `docs/new-product` 的页面和功能为产品目标，先通过页面原型验证完整交互，再由产品、UI、前端和系统架构等角色协作，自动补齐数据库、后端接口、安全、性能、状态管理、错误恢复和测试等缺失内容，最终形成真正可运行的完整系统。

用户明确指出：

- `new-product` 不是几个静态页面，而是完整产品的实验场和目标规格。
- 当前桌面端所有 UI 都需要迁移到 new-product 的新界面，而不是只修改某个页面或追加局部 CSS。
- 现有功能需要接入新 UI，不能用静态假数据替代真实的数据库、后端和 Agent 能力。
- 当前阶段优先写完整 PRD 和系统需求，暂不继续做局部 UI 修改。

## 2. 背景和问题

- 当前用户：使用 NoteMeld 进行本地知识工作、文件处理、Agent 执行、研究和产物管理的个人用户，以及云端用户、管理员、移动端用户和已配对设备用户。
- 当前场景：`docs/new-product` 已经描述了桌面端、云端、移动端、设计系统、功能注册表和部分交互原型；生产代码位于桌面前端、桌面后端、Cloud、iOS、Android 和 Harmony 等多端工程中。
- 当前痛点：原型页面与实际生产 UI、服务、状态、数据和系统边界尚未形成一一对应关系，导致页面看起来像 Demo，真实能力无法完整迁移，系统缺口也无法被稳定验收。
- 为什么现在要做：继续打磨静态视觉会放大尚未确认的功能和状态设计；需要先冻结一份完整需求，明确系统要实现什么，再进入架构、实现和最终 UI 精修。

## 3. 目标结果

### 3.1 产品目标

1. 将 `docs/new-product` 定义为 NoteMeld 新版本的产品规格、交互验证入口和生产 UI 验收基线。
2. 完成 `new-product` 规定的桌面端、Cloud、远程设备和移动端全部页面与功能，使真实能力在新信息架构中可用。
3. 在主框架中增加“应用”一级入口，将笔记、学习、监控和系统运行从旧设置/能力页中迁移为独立业务应用；应用内部拥有自己的导航和工作区。
4. 将页面上的功能与真实前端状态、服务/API、后端业务、数据库、权限和审计建立可追踪映射。
5. 对 prototype 或缺少后端的部分补齐可执行的系统设计，而不是把未实现能力伪装成已完成。
6. 在核心功能稳定后，统一优化所有端的视觉、交互状态、可访问性、响应式和性能；桌面端所有现有 UI 都必须迁移到新 UI，不保留旧 UI 作为最终入口。

### 3.2 系统目标

系统最终至少应能够可靠处理：

- 新建会话、选择 Workspace、输入任务、发送和取消。
- Agent Turn、工具调用、事件流、审批、失败、恢复、重试和终态。
- 文件、上下文、来源、产物、笔记和工作区引用。
- 会话列表、会话详情、归档、删除、分享和必要的恢复操作。
- 模型 Provider、模型选择、权限策略、MCP、Skill、插件和 Application。
- 后台任务、进度、日志、Agent 诊断和资源使用情况。
- 设置中的主题、账户、设备、数据迁移、安全和其他现有能力。

### 3.3 本轮交付范围

本轮不拆出“以后再做”的平台范围。以下内容全部属于本需求：

- 桌面端：D01、D03、D06、D09，以及 D09 对应的全部生产设置子页面。
- 应用层：APP01 笔记应用、APP02 学习应用、APP03 监控应用、APP04 系统运行应用。
- Cloud：C01-C06；C07 管理员审计合并到 C06 设置，不保留独立页面。
- 远程设备：设备配对、可信设备、运行节点、授权 scope、撤销和远程会话相关能力。
- 移动端：M01-M06，以及这些页面依赖的同步、缓存、记忆和存储能力。
- 基础设施：真实数据库、后端 API、Agent runtime、文件/Workspace、插件/Skill/MCP、认证授权、审计、任务执行、同步、迁移和测试。

`new-product` 是功能和交互的第一权威来源。生产代码中存在但未被 `new-product` 列出的能力，不自动获得新的产品入口；只有在实现已列功能所必需、或为安全/数据完整性所必需时，才作为隐含基础能力纳入，并必须在功能矩阵中标注。

### 3.4 应用边界与功能归属

用户已确认以下归属，后续实现不得再把这些业务能力塞回主框架的设置列表：

- APP01 笔记应用：笔记列表、样式与模板、Wiki 知识图谱/文章/关系/重建、旧笔记和 Markdown 导入。
- APP02 学习应用：学习空间、学习画布、掌握验证、复习，以及语义白板、卡片、关系和发布笔记。
- 插件能力：视频/音频/网页采集与导入、转写器和 Whisper 模型、下载器/Cookie/平台视频下载、OCR、视频帧提取、文档解析、证据锚点和知识切片审阅；这些能力由 D06 管理，应用通过 Host 消费结果。
- APP03 监控应用：Token 用量明细、供应商筛选、任务聚合，以及部署、GPU、CUDA、MCP、自动启动和插件/转写健康。
- APP04 系统运行应用：Agent Turn 诊断、Application 实例/项目目录/外部文件权限、candidate 验证/人工审批/安全声明、桌面更新、设备身份、LAN 优先、Relay 加密和远程帧。
- 导入/导出迁移包、合并、索引重建和迁移任务不在应用目录中展示；它们仍需作为底层系统能力真实实现并由受保护的系统流程调用。

本轮不要求兼容现有会话、笔记、设置或插件数据；允许清空和重建，但必须在初始化/迁移动作中明确告知影响范围并留下审计记录。

## 4. 非目标

当前总需求不直接承诺以下内容：

- 不把未被 `new-product` 或本需求明确纳入的额外产品功能自动扩张为本轮需求；必要的底层依赖除外。
- 不通过复制桌面业务逻辑的方式重写 Agent SDK、插件协议或其他独立仓库的核心运行时。
- 不为了视觉效果引入第二套组件库、第二套状态机、平行 API 或重复数据库。
- 不把静态原型中的占位、演示数据或未决能力宣称为生产完成。
- 不在需求尚未确认前生成执行 plan/spec 或大规模修改代码。
- 不在本需求中预先固定某一家第三方 Provider、邮件服务或对象存储供应商；但真实运行所需的适配接口、配置、故障处理和安全要求必须实现。

## 5. 当前系统事实

以下事实来自现有文档和代码盘点；没有明确证据的内容保留为待验证。

### 5.1 `new-product` 事实

- `docs/new-product/PAGE-MAP.md` 将桌面端定义为 D01 新对话、D03 会话列表与详情、D06 插件应用、D09 设置页面。
- `docs/new-product/design.md` 将 NoteMeld 定义为本地优先的开发者 Agent 工作台，而不是营销页；要求使用统一语义 Token、Lucide 图标、透明状态和可访问交互。
- `docs/new-product/config/feature-registry.json` 当前登记 37 个功能，其中 D01、D03、D06、D09 均仍标记为 prototype；C02 有 needs_backend 项；移动端部分数据能力也仍为 prototype 或 needs_backend。
- `docs/new-product/config/feature-registry.json` 同时登记 APP01–APP04；应用原型状态不能被当作后端已完成，必须继续映射到真实 service/API、数据权威、权限和测试。
- 原型支持 Preview 和 Explain 两种模式；绑定的 selector、feature registry 和产品文档是解释功能映射的依据。
- 原型规定 D01/D03 共享 Agent、侧边文件面板和底部命令行/日志面板结构；面板需要独立控制。

### 5.2 生产代码事实

- 桌面前端入口为 `desktop/frontend/src/App.tsx`，当前包含 `/new`、`/notes/:taskId`、`/applications`、`/settings/*`、`/cloud` 和 `/mobile/*` 等路由。
- 桌面前端已有 Home、Capability Center、Settings、Cloud、Mobile 等页面和服务层，已有能力不能被迁移过程删除或用假实现替换。
- 桌面前端已有会话、Agent、Workspace、模型、上传、插件、MCP、设备、迁移、用量、Wiki、学习和白板等服务入口；具体 API 语义以现有 router、service 和 `docs/system/api-inventory.md` 为准。
- 实际桌面端仍存在大量设置子页面，D09 的生产迁移范围需要覆盖这些子页面的入口、状态和危险操作，而不仅是一个设置首页。
- 当前工作区存在用户已有改动；后续实现必须按仓库规则保护这些改动，不进行无关清理或覆盖。

### 5.3 数据与系统边界事实

功能注册表已描述 users、access_requests、workspaces、workspace policies、sessions、commands、events、approvals、models、devices、grants、audits、conversations、conversation_messages、agent_turns、agent_events、note_documents、plugins、providers 等数据职责，但部分桌面和跨端模型仍处于 prototype 或待验证状态。

系统必须继续区分：

- 本地会话、云端会话和远程设备会话。
- 用户设备和云端运行节点。
- Workspace authority、用户个人偏好和组织级记忆。
- Agent 事实状态和 UI 展示状态。
- 文件正文、上下文引用、产物索引和分享投影。

## 6. 角色协作模型

四个角色是同一条需求链上的职责视角，不是四套互相独立的实现：

### 产品经理

- 从 `new-product` 提取用户任务、主流程、优先级和页面范围。
- 定义正常、空、加载、运行、审批、失败、取消、恢复和完成状态。
- 将“看起来高大上”转换为可观察、可验收的产品行为。

### UI/UX 设计师

- 将已确认的产品流程组织为统一的桌面端页面结构和设计语言。
- 复用 `new-product/design-system` 的 Token、原语和交互规则。
- 设计真实数据长度、异常反馈、危险操作和高密度工作区，而不是只做静态截图。

### 高级前端工程师

- 将 D01/D03/D06/D09 及 D09 子页面迁移到新 UI。
- 复用现有服务、状态和组件边界，补齐交互状态、键盘焦点、响应式和性能处理。
- 保持 selector、功能绑定和真实业务行为可追踪。

### 系统架构师

- 检查每个 UI 行为是否有真实的 API、数据权威和状态来源。
- 补齐数据库、迁移、权限、安全、幂等、并发、审计、缓存和恢复策略。
- 保证 Agent SDK、宿主、插件、Cloud、设备和本地存储的职责边界不被 UI 迁移破坏。

四个角色的决策顺序为：产品真实性和安全 → 既有系统契约 → 可访问性与交互可靠性 → 视觉表达 → 实现便利性。

## 7. 用户故事

- 作为 NoteMeld 本地用户，我希望从新对话开始选择 Workspace 并执行任务，以便在一个清晰的工作区内完成研究、文件处理和 Agent 工作。
- 作为会话用户，我希望看到 Agent 的真实执行过程、工具调用、审批和产物状态，以便知道系统正在做什么、是否需要我介入以及失败后如何恢复。
- 作为会话用户，我希望在同一套新 UI 中查看文件、上下文、来源、产物和日志，以便不需要在旧页面和新页面之间切换。
- 作为插件/能力管理用户，我希望看到能力来源、版本、兼容性、权限、安装状态和错误，以便安全地安装、启用、禁用、更新或撤销能力。
- 作为设置用户，我希望模型、设备、数据、安全和诊断入口拥有一致的信息架构，并对危险操作提供明确的确认和恢复语义。
- 作为系统维护者，我希望页面显示的状态来自真实持久化状态和事件，而不是前端自行推断，以便问题可以复现、审计和恢复。

## 8. 验收标准

### 8.1 需求和映射

1. GIVEN D01、D03、D06、D09 的页面清单，WHEN 需求进入 Ready for Plan，THEN 每个页面的主流程、次要流程、权限、状态、错误和验收标准均已列出。
2. GIVEN `feature-registry.json` 中的功能，WHEN 进行实现规划，THEN 每个桌面功能都能追踪到页面元素、前端状态、service/API、后端模块、数据表和测试；未实现项明确标记为 prototype、needs_backend 或待验证。
3. WHEN 发现原型文档、代码、数据模型或 API 之间存在矛盾，THEN 需求文档保留冲突和证据，不通过猜测消除冲突。

### 8.2 全端迁移

4. GIVEN 用户进入桌面端、Cloud、远程设备入口或移动端，WHEN 打开本需求范围内的页面，THEN 页面使用 `new-product` 规定的统一语义、Token、原语和平台适配布局。
5. GIVEN 现有功能已经有真实 service/API，WHEN 迁移到新 UI，THEN 用户可以在新页面执行真实操作，旧功能不会仅保留在不可达的旧 UI 中。
6. GIVEN D09/C06 包含多个设置和管理子页面，WHEN 用户从设置导航进入任一子页面，THEN 入口、权限、加载、保存、失败、取消和危险操作均有明确状态；管理员审计位于 C06 设置中。
7. WHEN 用户在窄桌面窗口、移动端、深色主题或长文本数据下操作，THEN 页面不发生不可读截断、面板覆盖关键操作或状态语义丢失。

### 8.3 Agent 与数据真实性

8. GIVEN Agent 正在运行、等待审批、被取消、失败或已完成，WHEN 用户查看会话，THEN UI 同时展示可理解的文字、图标和语义状态，并且状态来源可以追溯到持久化记录或事件流。
9. WHEN 用户重复发送、刷新、重新打开或恢复一个会话，THEN 系统不会产生重复副作用、丢失事件、错误覆盖终态或创建无法关联的孤立记录。
10. WHEN 文件、Workspace、产物或来源不可用，THEN 系统明确说明不可用原因，并提供安全、可逆或可重试的下一步；不会把不可访问内容显示为已成功读取。

### 8.4 安全、性能和验证

11. WHEN 功能涉及本地文件、Provider secret、设备授权、MCP、插件或远程执行，THEN 权限边界、敏感信息处理、确认、撤销和审计规则已在需求和实现中明确。
12. WHEN 处理长会话、大量消息、长任务、多个事件、大量笔记/图谱节点或大量监控数据，THEN 需求定义分页/虚拟化、缓存、取消、超时、资源上限和恢复策略，并有可执行的性能验证。
13. WHEN 全端核心链路完成，THEN 至少通过各端前端类型/契约、后端相关测试、数据迁移/状态测试、浏览器/桌面/移动端纵向测试和构建验证。
14. WHEN UI 实现声称完成，THEN 已检查宽桌面、窄桌面、移动端、浅色、深色、空、加载、运行、审批、失败和完成状态；不能只凭单张静态截图验收。

## 9. 输入 / 输出样例

### 输入

- `docs/new-product/pages/desktop/d01.html`、`d03.html`、`d06.html`、`d09.html` 及其 CSS/JS。
- `docs/new-product/design.md`、design-system、feature registry 和 PAGE-MAP。
- 当前桌面前端页面、组件、服务、路由、后端接口、数据库和已有测试。
- 用户确认的产品优先级、范围取舍和未决业务规则。

### 输出

- 一份 Ready for Plan 的 canonical PRD。
- 桌面端完整功能矩阵和状态矩阵。
- 前端/后端/API/数据库/安全/性能映射。
- 经过确认的实施 plan、spec、测试证据和系统文档回写。
- D01/D03/D06/D09 的真实生产 UI 以及可验证的功能闭环。

### 反例或失败样例

- 只修改 `docs/new-product` 的 HTML/CSS，生产 React 页面仍是旧 UI。
- 只在 React 页面外包一层新样式，但按钮没有接入真实 API 或状态。
- 用固定进度条、假会话、假产物或前端本地状态掩盖后端缺口。
- 只实现成功路径，没有审批、取消、失败、恢复、权限拒绝和旧数据兼容。
- 为了赶视觉效果重复创建组件库、数据库表或 Agent 状态机。

## 10. 约束

- 平台 / 设备：本轮覆盖桌面端、Cloud、远程设备和移动端；必须考虑桌面窗口大小、移动端触摸、浅色/深色主题、键盘操作、Electron/Tauri 以及各移动端运行环境。
- 架构：遵守 NoteMeld 工作区和各子仓库的依赖方向；Agent SDK 保持唯一运行时事实源；不复制 Agent loop。
- UI：复用 `new-product` 的 Token、原语、Lucide 图标和功能 selector；不建立平行设计系统。
- 数据：不得凭猜测改数据库字段、状态机、API、schema、ABI 或跨语言语义；所有未知项标记为待验证。
- 隐私 / 安全：密钥、Cookie、设备私钥、用户文件正文和敏感运行数据不得进入日志、fixture、分享或文档。
- 兼容性：不要求兼容当前会话、笔记、Workspace、Provider、插件和设置数据；允许清空或重建数据。但清空/重建必须是明确、受保护、可审计的迁移动作，不得在用户无感知的情况下发生。
- 性能：长会话和长任务不能阻塞首屏或无限制增长内存；具体指标待结合现有基线和用户优先级确认。
- 交付：需求未达到 Ready for Plan 前，不进入大规模实现；实现不主动提交、推送或创建 PR，除非用户另行确认。

## 11. 边界场景

- 空数据：没有会话、Workspace、文件、插件、Provider、设备或产物时，页面显示可行动的空状态。
- 加载：首次加载、懒加载、事件追赶、文件读取和长任务期间显示真实加载状态，不阻塞无关区域。
- 权限拒绝：Workspace 文件、Provider、MCP、插件、设备或远程执行权限被拒绝时，说明原因并保留用户输入和当前任务。
- 网络/服务失败：Cloud、Provider、下载、同步或后端不可用时，显示错误范围、重试、取消和离线/本地替代路径。
- Agent 中断：用户取消、进程崩溃、电脑休眠、窗口关闭或网络中断后，会话状态、事件和恢复入口保持一致。
- 审批：高风险操作必须暂停在明确的待审批状态；批准、拒绝、过期和撤销不能被伪装成普通成功/失败。
- 重复操作：重复点击发送、保存、安装、撤销、删除、导入或恢复不会产生重复副作用。
- 数据重建：本轮允许清空旧会话、旧笔记、旧设置和旧插件元数据；重建前必须明确提示影响范围，并保证新 schema、索引和初始数据可完整初始化。
- 大数据量：长会话、大量会话、多个文件、长日志和高频事件不应导致不可用的渲染或内存增长。
- 多端边界：本地会话、云端会话、远程设备会话、用户设备和运行节点在页面文案和权限上不能混用。
